1. Introducción

  
OAuth se diseñó para dos tipos de llamador. Un agente no es ninguno de los dos, y esa grieta ya está en producción.

  

    
+-----------------------+
| Persona               |
| frente a una pantalla |
| acepta el consent     |
+-----------------------+

    
+-----------------------+
| Servicio              |
| con credenciales      |
| propias               |
+-----------------------+

    
ninguno de los dos
+-----------------------+
| Agente de IA          |
| llega con tu token    |
| y decide solo         |
+-----------------------+

  

  
El usuario aprobó una vez, para algo puntual. Después el agente actúa solo, en loop, a velocidad de máquina.

7.2. Registrar quién decidió, o no ejecutar

  

    
claims, nunca el bearer

    

      
Dos identidades por evento: act (el agente) y sub (la persona), más la request que lo originó.

      
Se guardan los claims. El bearer, MUST NOT.

      
Si no hay broker o el audit no escribe: deny.

8. Consideraciones de seguridad: el lunes

  

    
[ ]Pedí ver el token decodificado. Si no podés leer aud y scope, no lo conectes.

    
[ ]Un token por acción: una audience, un scope, minutos de vida.

    
[ ]El refresh token nunca entra al contexto del agente.

    
[ ]El resource server valida audience y scope en cada operación.

    
[ ]Cada evento registra act, sub y la request que lo originó.

  

  
APROBADO

  
Límite del laboratorio: no usa DPoP (RFC 9449). Un access token robado sirve hasta que vence; por eso vence en minutos.
